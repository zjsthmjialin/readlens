# ReadLens 部署形态方案（四选对比）

> **决策（2026-08）**：ReadLens 定位为**分发给别人用**，目标是安装方便、上手容易、
> 功能丰富。据此选定 **① GitHub 仓库打底 + ④ pip 包分发** 组合并已落地：
> - `pip install readlens`（或 `pipx install readlens`）即可安装；
> - `readlens quickstart` 一条命令用内置离线数据生成演示知识库，无需 Key；
> - `pyproject.toml` 元数据/入口点、GitHub Actions CI（pytest + CLI 冒烟）已就绪。
> 形态②定时导入需真实微信读书 Key，形态③ Skill 包按需再做（见文末推荐组合）。
>
> 下方保留四形态完整对比，便于后续复盘与扩展。

先说结论：这四种**不是互斥单选**，而是「地基 + 上层」的关系。
GitHub 仓库是所有其他形态的地基；定时任务 / Skill 包 / pip 包都建立在它之上。
建议的落地顺序：**先 GitHub 仓库打底 → 再按使用场景加定时任务或 pip 包 → Skill 包最后**。

---

## 形态一：GitHub 仓库 + Release

把项目整理成规范开源仓库：README、`requirements.txt`、`LICENSE`、CI 跑 `pytest`、
打 tag 发 Release（附 `examples/output` 里的示例产物截图）。

**优点**
- 一切的地基：版本管理、Issue、协作、CI 质量门槛都在这里。
- 门槛最低、最通用：任何人 `git clone` + `pip install -r requirements.txt` 即可跑。
- 与项目现状最贴合——已有 `docs/`、`tests/`、`examples/`，几乎是「整理」而非「重写」。
- 天然承载其他三种形态（定时任务的脚本、pip 打包配置、Skill 包都放在同一仓库）。

**缺点**
- 对纯使用者（不写代码）仍需命令行，不如「一键」友好。
- 只做到「可获取」，没解决「自动运行」或「一键安装」。

**工作量**：低（0.5–1 天）。补 `LICENSE`、完善 `README`、加 GitHub Actions 跑 pytest、
把 `config.yaml`/`.env` 纳入 `.gitignore`（已在 HANDOFF 提示）。

**适合**：作为第一步，无条件先做。

---

## 形态二：定时自动导入（scheduled task）

用调度任务周期性：拉取阅读数据 → 增量更新 vault → 生成周报/月报推送。
依赖本轮刚做的**增量更新**（重跑不覆盖手写内容），这是它成立的前提。

**优点**
- 真正把 ReadLens 变成「活」的知识库：数据自动流入，无需手动跑命令。
- 增量更新已就绪，重复运行安全——这条路的技术前提本次已打通。
- 价值最高：从「工具」升级为「后台服务」。

**缺点**
- **需要真实微信读书 Key**，且 `weread` 适配器尚未联调（HANDOFF 已知限制）。
- 需要一个常驻运行环境（本地 cron / 服务器 / GitHub Actions 定时 / Cowork 定时任务）。
- Key 的安全存储与失效处理要额外设计。

**工作量**：中（联调 weread 1–2 天 + 调度接入 0.5 天）。

**适合**：你自己日常持续使用、且愿意接真实 Key 时的「终局形态」。可作为第二步。

---

## 形态三：Skill 包（`npx skills add` 形态）

打包成原项目 Tencent/WeChatReading 那种可分发的 Skill 包，供 Agent 一键安装调用。

**优点**
- 回归项目「脱胎于 WeChatReading Skills」的初心，形态最契合来源。
- 对 Agent 生态友好：别人能在自己的 Agent 里直接装来用。
- `skills/*.md` 已经是面向 Agent 的能力说明，有现成基础。

**缺点**
- 受众最窄：只有用相应 Agent/Skill 体系的人才用得上。
- 打包规范、清单、依赖声明要按 Skill 体系重做一遍，收益不一定匹配工作量。
- 与「个人日常用」目标关系较弱——更偏「对外分发」。

**工作量**：中（需研究目标 Skill 体系的打包规范，1–2 天）。

**适合**：当你想把 ReadLens 作为**能力对外分发**给 Agent 生态时。建议放最后。

---

## 形态四：pip 包 / CLI 分发（PyPI 或私有源）

把 `readlens` 打成可 `pip install readlens` 的命令行工具，加 `pyproject.toml` 与
console_scripts 入口（现在已是 `python -m readlens.cli`，改造成本低）。

**优点**
- 使用者体验好：`pip install readlens && readlens vault ...`，无需 clone。
- Python 生态标准做法，依赖/版本管理规范。
- 与 CLI 现状高度契合，改造量小。

**缺点**
- 发 PyPI 需要账号、命名、版本维护；私有源则需自建。
- 仍是命令行工具，不解决「自动运行」。
- 对「就我一个人用」的场景，收益不如直接 clone 明显。

**工作量**：低–中（加 `pyproject.toml` + entry point 半天；发 PyPI 另算）。

**适合**：当有**多个使用者**、希望「装一下就能用」时。可与形态一并行。

## 对比速览

| 维度 | ① GitHub 仓库 | ② 定时自动导入 | ③ Skill 包 | ④ pip 包 |
|------|--------------|---------------|-----------|---------|
| 主要价值 | 地基 / 可协作 | 自动化「活」库 | 对 Agent 分发 | 一键安装 |
| 受众 | 开发者/自己 | 自己（重度） | Agent 生态 | Python 用户 |
| 前置依赖 | 无 | 真实 Key + weread 联调 | Skill 规范 | 打包配置 |
| 工作量 | 低 | 中 | 中 | 低–中 |
| 是否解决「自动运行」 | ❌ | ✅ | ❌ | ❌ |
| 是否解决「易安装」 | 半 | — | ✅(Agent) | ✅ |
| 与项目现状契合度 | 高 | 中 | 中 | 高 |

## 推荐组合（供讨论）

1. **现在**：形态① GitHub 仓库 + Release 打底（低成本、无前置依赖，且是其余三者的载体）。
2. **接着按你的真实用途二选一**：
   - 若目标是「自己日常自动更新知识库」→ 走**形态②定时导入**（需先联调 weread + 配 Key）。
   - 若目标是「让别人也能装来用」→ 走**形态④ pip 包**（改造量小）。
3. **形态③ Skill 包**：等前面稳定、且确有对外分发 Agent 能力的需求时再做。
